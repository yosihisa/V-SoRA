# 実観測を処理するための準備

## VDIFだけでは条件が足りない

VDIFは電圧sampleを局識別・時刻等とともに運ぶための標準形式です。ただし、その時刻が実sampleに正しく対応するという証拠や、アンテナ位置・RF設定・較正情報をすべて保存する形式ではありません。

| 必要な情報 | 何に使うか | 現時点での状態 |
| --- | --- | --- |
| sample番号とUTC、測定法、不確かさ | 異なる局で同じ瞬間の電圧を選ぶ | 実機測定が必要。PCのUSB到着時刻だけでは不十分 |
| 公称/実sample rate、適用時間 | 時間とともにずれるsampleを補間する | 短い区間の線形clockモデルを入力できる |
| 局位置、座標系、位置誤差 | 幾何delayとu,v,wを計算 | 現在の例は仮想地点とENU位置 |
| 天体位置、基準座標系 | 位相中心を決める | ICRSの赤経・赤緯を使う |
| RF中心、帯域、I/Q順序・符号 | 周波数と位相の向きを決める | 限定profile。実RTL-SDRの符号は実測確認が必要 |
| bit深度、量子化scale | 記録値から電圧値へ戻す | 8bit complex、4096sample/frameを検証 |
| 欠損・無効区間・収録設定変更 | 不正なsampleを除外 | frame invalidを扱う。frame内の欠落詳細は別情報が必要 |
| 利得・位相・delay・LO差 | 受信機応答を取り除く | 模擬点源または形状モデルで較正可能 |
| bandpass、偏波、主ビーム、感度 | channel差・偏波・絶対fluxを正しく扱う | 実機の測定・較正手順が未完成 |

OCXO/GPSDOの採用と、時刻・sample・位相が実際に揃ったかは別に確認します。現状のソフトは未知の弱い天体から、すべての時計情報を自動復元する完成品ではありません。

## 現在の処理順

1. 原本VDIFを保存し、checksum・局・sample数・無効区間を確認する。
2. 観測条件とsession manifestを用意する。[manifest規約](../../interfaces/session-manifest.md)にある項目を埋める。
3. 実時計の情報があれば`correlate-aligned`を使う。[clock規約](../../interfaces/clock-model.md)の短区間制限を守る。時計情報がないまま仮の値で実観測精度を保証しない。
4. RFI診断または既知の妨害channelの手動除外を使う。短い積分では統計量不足になることがある。
5. 短積分の相関から、既知天体を使って局の振幅・位相・delay・rateを推定する。
6. rate補正をIQへ戻し、再相関してから較正し直す。初回の長い平均で失った情報を隠さない。
7. 較正済みの相関値をJy単位で保存し、FITS-IDIと画像へ進む。CASAを使う場合は[重み保持アダプター](../../interfaces/fitsidi-profile.md)を通す。
8. 条件・失敗・入力識別情報・結果を一緒に残す。

生ADCの相関はADC²です。量子化scaleを設定してもJyへの較正にはなりません。現在の画像ソフトは未較正ADC入力を拒否します。

## 容量の例

sample rate2.048MHz、8bit I+8bit Qなら、一局は約4.096MB/sです。4時間で約59GB、8局で約472GBになります。これは計算値です。VDIFヘッダー・作業コピー・バックアップを加えるとさらに増えます。

相関出力も、短い積分・多数channelで長時間保存すると大きくなります。まず短い較正区間を処理し、時計と位相を合わせてから平均時間を長くする設計が必要です。現状のPython参照実装の全観測速度は未測定です。[容量とPC構成の設計](../design/2026-10-02-operational-architecture.md)に仮定を分けて記載しています。

## 次に実機から欲しい測定

共通の強い試験信号で、I/Qの向き、sample開始差、実sample rate、LOの差、温度による変化、欠損を調べるのが最初の候補です。その後、アンテナ・受信機の感度とRFI環境を測り、Cas Aの較正に使う天体・モデルを選びます。具体的な試験接続はハードウェアの仕様が判明してから決めます。

実測局位置や装置serialなどはローカルの観測データとして管理し、公開リポジトリへ個人の所在地や識別情報を入れません。公開例は仮想地点とST01などの局IDを使います。
